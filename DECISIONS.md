# DECISIONS

Non-obvious choices made during development, with reasons.

1. Interpreter. The spec requires Python 3.11+, but the default `python` on this machine is 3.10.11 (the spec's definition of done also says `python run_demo.py`). Resolution: all development and measured runs used `py -3.12` (3.12.2); the code deliberately avoids 3.11-only syntax so the plain `python run_demo.py` invocation also works here. Declared target stays 3.11+.

2. Model pool. `GET /models` on `https://api.z.ai/api/paas/v4` lists the glm-4.5 through glm-5.3 families. With the current `ZAI_API_KEY`, every glm-5.3-family model returns HTTP 1113 "Insufficient balance or no resource package"; only `glm-4.5-flash` completes real calls, so it is the backbone default. The model name is configurable with `--model`, and `--backend scripted` runs fully offline. The scripted backend reports zero calls and zero tokens and never estimates token counts.

3. Guard evaluation, pure Python first. File checks (`file_exists`, `file_hash`, `dir_listing`) are stdlib-only. The one command guard is not a shell escape: it launches the current interpreter with a snippet from a fixed in-code allowlist (a single `ast.parse` one-liner), cwd pinned to the cache root, every path argument resolved and rejected if it escapes the root, 10 s timeout, non-whitelisted snippets refused before any execution. Chosen over a general sandbox because the demo needs exactly one external check and a general runner would be a larger attack surface than the problem warrants.

4. Signature vs guards. The context signature is task identity (task_id, path, instruction); guards carry all environment sensitivity (input file contents, directory listing, post-state). This split is what makes guard misses observable: a changed file produces a signature hit that guards then reject, which is the behavior the measurement wants to count.

5. Post-state pinning for write decisions. A cached write guards the exact content it wrote, not the pre-state it read, because replay is an idempotent write and reuse is valid exactly while the file equals the decision output. Pre-state pinning was tried first and has a mirrored flaw in chained pipelines (later tasks overwrite the input the decision was made on). Consequence, documented in README: two cached tasks writing the same file supersede each other's guards, so the workload uses one decision per target file.

6. Line-ending normalization in hashes. Windows `write_text` emits CRLF, so naive byte hashing made every guard fail. `sha256_file` and `sha256_text` normalize CRLF and CR to LF before hashing, on both the pin side and the check side. Guards therefore compare text identity modulo line-ending style; binary files are out of scope.

7. Response extraction uses sentinels. The first LLM run leaked a stray fence-language line ("text") into a rewritten README when the model returned a bare fence with the language word on the next line. Prompts now ask for content between BEGIN_CONTENT and END_CONTENT lines, with a fenced-block fallback that drops a lone leading language word.

8. One flat cache level, no recursion. The spec requires stating this plainly: there is no decision graph and no self-improvement loop beyond replaying one stored decision. Recursive application would require verified composition between decisions, which the guard model here does not attempt.

9. No packaging metadata. The spec's layout has no pyproject.toml, so `run_demo.py` and `tests/conftest.py` insert `src/` (and `examples/`) into `sys.path`. Adding a build step would be scaffolding the spec did not ask for.

10. Workspace and cache lifecycle. `examples/workspace/` is deleted and rebuilt deterministically at the start of every demo run, and the cache JSON lives inside it, so runs never inherit stale state from a previous demo. The directory is gitignored. `results/results.csv` is committed and regenerated by each measured run.

11. Guard misses are counted, not silently absorbed. A stale hit increments a counter and forces a fresh decision that overwrites the entry. The alternative (revalidating and keeping the old entry) would hide exactly the event the measurement is supposed to report.
